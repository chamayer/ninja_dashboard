## Validation and next action

### Completed cycle and query evidence

The observed chain completed: source-refresh 16:36:15–17:06:33 UTC (1,818 s),
resolver 17:06:33–17:10:37 (244 s), platform-evaluate 17:12:12–17:34:02
(1,310 s; 4,852 affected rows). Total elapsed span was about 58 minutes against
an hourly source interval. Other completed work immediately started a further
platform evaluation. The active backlog progressed; it was not an idle spin.

The three Ninja application containers were recreated at 17:12:07 UTC during
observation, interrupting one health evaluation. This investigation did not
initiate that recreation. The restart gap and competing host workloads mean
these observations are not a controlled benchmark. Existing migration 0394's
guard optimization was already deployed; latest recorded migration was 0399.

Over 30.20 seconds at 17:34 UTC, PostgreSQL counters increased by 644,546 blocks
read into shared buffers, 53,395,456 temporary bytes, 2,790 inserted tuples,
and 1,485 updated tuples. Buffer misses can be served from the OS cache; they
are not proof of physical disk reads. Live host disk reads and I/O waits were
also visible. PostgreSQL shared_buffers is 128 MiB. No tuning change is justified
solely by buffer size or cumulative counters.

### Other host workloads

- SentinelOne was confirmed by its systemd cgroup. In one 30-second window,
  agent CPU was approximately 82.5% of one core and scanner CPU 9.7%.
- Zabbix's SNMP poller is its dominant server process (about 88.5% cumulative
  process CPU and substantial instantaneous activity). Database shared_buffers
  is approximately 8.8 GiB; container memory was approximately 8.9 GiB.
  Item cadence inventory includes many one-minute checks. Configuration and
  monitoring policy were not changed. Do not use Zabbix for parser monitoring.
- Graylog's main JVM accounted for approximately 31.3% of one core in the same
  30-second window and held approximately 2.35 GiB of process swap. Its data
  node also uses several GiB of resident memory.
- A UniFi JVM lives in a rootless Podman container, outside Docker statistics.
  It has approximately 4 GiB resident memory and used approximately 35.7% of
  one core over a separate 30-second window.
- DMARC's two request threads together used approximately 45.6% of one core in
  the first window, despite instantaneous peaks above 100%.

Full swap occupancy did not establish continuous thrashing: interval samples
showed small swap-ins, no swap-outs, and low memory PSI. CPU, data reads, and
multiple services are contributing. Do not sum PostgreSQL worker RSS values;
shared mappings would be counted repeatedly.
